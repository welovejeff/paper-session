# Contributing to Paper Session

The goal of this project is narrow and worth stating before anything else:
**increase the surface area for doing human things in an agentic future of
thought work.** A contribution is good if it makes a person more likely to take
a pen somewhere quiet and come back with thinking that is actually theirs.

That goal implies an unusual bar for changes, described below. Please read the
bar before writing code — several categories of well-intentioned improvement are
deliberately rejected here, and it's better to know that first.

## Setup

```bash
git clone https://github.com/welovejeff/paper-session.git
cd paper-session
python3 -m pip install -r requirements.txt

# work on the skills locally
ln -sfn "$PWD/paper-session" ~/.claude/skills/paper-session
ln -sfn "$PWD/scan-back"     ~/.claude/skills/scan-back
```

Symlinking means your edits take effect on the next session with no rebuild
step. Use `./build.sh` only when you're ready to update the committed bundles.

## Source layout, and what not to edit

The **unpacked directories are the source.** `paper-session.skill` and
`scan-back.skill` are build artifacts, committed so people can install without
cloning.

```
paper-session/          ← edit this
scan-back/              ← and this
paper-session.skill     ← generated by ./build.sh, do not hand-edit
scan-back.skill         ← generated by ./build.sh, do not hand-edit
```

Never edit a `.skill` file directly, and never open a PR that changes only a
bundle — a zip diff is unreviewable, which is the whole reason the source is
unpacked. Run `./build.sh` as the last step of your change and commit the
regenerated bundles with the source edit.

`build.sh` fails the build if a skill's `SKILL.md` declares a `name:` that
doesn't match its directory, or if the font license would ship detached from the
fonts.

## The bar for a new rule

**A change to what gets printed needs a source in
`paper-session/references/evidence.md`, stated with its limitations.**

The research grounding is this project's whole moat. Design intuition is very
welcome in issues and discussion and is not sufficient in the spec. If you
believe a rule is right but can't source it, open an issue rather than a PR —
that's a genuinely useful contribution and it may be that the citation exists
and neither of us has found it yet.

Two honest asymmetries in this rule:

- **Removing or weakening a rule needs less evidence than adding one.** If a
  rule's cited support turns out to be thinner than the brief represents, saying
  so is high-value even without a replacement.
- **Wording, layout, and code changes that don't alter what a sheet asks of a
  human need no citation at all.** Fixing a typo, tightening prose, making the
  verifier faster, adding A4 support: just open the PR.

## The bar for a capability change

Changes to how the project itself works — a new distribution channel, a build
or CI change, a restructuring — follow a parallel rule: **research first, then
an implementation PR that answers to the research.** A numbered brief lands in
[`research/`](research/) stating findings, a recommendation, and — most
importantly — what it could *not* confirm; the implementation PR tests those
unknowns before building on them, appends what it found, and flips the brief's
status. The whole process is one page: [`research/README.md`](research/README.md).

Small tooling tweaks don't need a brief, the same way typo fixes don't need a
citation. Write one when being wrong is expensive.

Note the boundary: `research/` is for the project around the skills. Research
about what gets printed on a sheet still lands in
`paper-session/references/evidence.md`, and only there.

## Where things go

The three-layer structure is load-bearing, and the dependency runs one way:
`SKILL.md` → `references/` → `evidence.md`.

| Change | Goes in |
|---|---|
| A new activity zone or sheet pattern | `references/page-patterns.md` |
| How a prompt should be worded | `references/prompt-craft.md` |
| Point sizes, gray values, rule weights, page anatomy | `references/design.md` |
| A research finding and its limitations | `references/evidence.md` |
| Procedure — when the skill acts, in what order | `SKILL.md` |

Rules in `SKILL.md` are **compressed restatements** of reference rules, never
inventions. If you add a rule to `SKILL.md`, it must already exist in a
reference. If you change a rule in a reference, check whether `SKILL.md`
restates it and update both, or the skill will contradict its own reference
halfway through a session.

### The one cross-skill coupling

The **pen protocol** — ink colors, mark vocabulary, and the authority cascade —
is specified in two places with no shared file:

- `paper-session/references/design.md` §9, which prints the ink key
- `scan-back/SKILL.md` Step 1, which reads it back

**A change to either must be made in both.** Otherwise a sheet prints a key that
`scan-back` doesn't honor, which is worse than having no protocol.

## Testing a change

There is no unit test suite; the artifact is a PDF and the failure modes are
visual. What we do have:

```bash
python3 paper-session/scripts/verify_layout.py yoursheet.pdf
```

This is **mandatory** and it gates the skill itself, not just CI. It fails on
text escaping the page bounds and on colliding text — both across baselines and
on a shared baseline, which needs its own glyph-level check because pdfplumber
merges same-line overlapping characters into one word. Those are the defects
that survive casual inspection and ruin a sheet at the printer. It checks
geometry and never taste.

For anything that changes a sheet's appearance, also do the thing the project is
about:

1. Generate the sheet.
2. **Print it.** On a consumer inkjet, in grayscale, on cheap paper.
3. Fill it in with an actual pen.
4. Photograph it with a phone in imperfect light and hand it to `scan-back`.

Include a photo in the PR. A sheet that looks correct on screen and fails at
step 2 or 4 is a defect the verifier cannot catch, and screen review has missed
these before.

## What gets rejected

Both `SKILL.md` files end with an anti-pattern list. Those are not style
preferences — each one has evidence behind it, and re-adding any of them breaks
the premise rather than just making an uglier sheet. The most frequently
proposed:

- **Example answers in a creative zone**, "just to get them started." This is
  design fixation, the most replicated finding in the field. Ideas come to
  resemble the example, across fewer distinct categories. Telling people not to
  copy does not help.
- **A suggested duration or time estimate**, anywhere. Time pressure is the
  specific trigger for shallow processing, and the creativity benefit of input
  constraints holds only in its absence.
- **A scoring matrix, rubric, or weighted criteria** on a selection zone.
  Deliberative selection performs at chance; rubrics don't improve accuracy.
- **"Try not to be influenced by the above."** Groups told to avoid an example
  incorporated its features at the same rate as groups told nothing. The layout
  has to do the work.
- **Encouragement microcopy** or exclamation marks. Warmth comes from
  directness. Congratulating someone on a blank page costs credibility on a page
  that is otherwise honest.
- **Denser layout** to "use the space better." At least half of every page is
  space for the pen, by law. If a blank sheet looks finished, it's wrong.
- **Making the AI keep working the problem** after the sheet is handed over.
  Stopping is the feature.

If your change makes a *blank* sheet look more impressive, it is probably wrong.
The completed page is the finished design.

## Especially wanted

- **Session reports.** Which sheets get completed and which get abandoned.
  Completion rate is the metric that matters and nobody has data yet. There's an
  issue template for this and it may be the single most useful thing you can
  file. Reports land in the Field reports tier at the end of
  `paper-session/references/evidence.md`, below the lab evidence: three
  independent reports agreeing on the same failure open a pattern-review issue,
  and a field report alone never adds a rule.
- **Counter-evidence.** A citation weaker than the brief represents, or a
  failed replication we've missed.
- **Non-Letter paper sizes.** A4 is the obvious gap and touches
  `references/design.md` throughout, since every measurement is in points off a
  612×792 page.
- **Patterns for uncovered domains** — teaching, therapy, law, field science,
  music, kitchen work.
- **Better transcription heuristics** in `scan-back`, particularly for spatial
  arrangements and photographed card layouts, where the *position* is the answer.

## Pull requests

- One concern per PR. A new pattern and a design-system change are two PRs.
- Say what a human does differently because of your change. If the answer is
  "nothing, but the code is nicer," that's a fine PR — just say so, so it gets
  reviewed as a refactor and not as a behavior change.
- Cite your source inline for any rule change.
- Run `./build.sh` and commit the regenerated bundles.
- Prose is part of the product here. Match the existing voice: direct, second
  person, no hedging, no filler. If it reads like a corporate worksheet, it will
  be edited until it doesn't.

## Reporting conduct concerns

`CODE_OF_CONDUCT.md` (Contributor Covenant 2.1) applies to this project. Report
anything that needs reporting by opening an issue, or — if you would rather not
raise it in public — by contacting [@welovejeff](https://github.com/welovejeff)
directly through GitHub.
